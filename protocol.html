What the experiment does, step by step

The question is whether the index configuration that wins on a sample of the database is the same one that wins on the full database, and whether that depends on how the sample is built.

TPC-DS, PostgreSQL 14, 99 queries. A configuration is a set of indexes. Ground truth is a real CREATE INDEX and a measured runtime, not optimizer cost. This page is the procedure. The numbers are in results.html.

1. The question in one picture

Wu et al. showed that the cheapest plan under the optimizer is often not the fastest plan when you run it. Checking that properly means building indexes and timing them, which is expensive. The sample is supposed to be a cheaper stand-in for that check.

2. The six steps Srinivas asked for

1Generate candidate configurations. A configuration may contain more than one index.

→

→

→
5Evaluate the same workload on D'.
→
6Compare rankings: Kendall tau, top-1, evaluation cost reduction.

All 99 queries are kept. Candidates come from several models, not only HypoPG.

3. How a configuration is made

The advisor sees the schema, the existing primary keys, and the 99 query texts. It does not see the data and does not run SQL. Each model writes five sets of at most eight indexes.

  1. Six models, isolated: Claude Opus 5, Claude Fable 5.1, GPT 5.6 Sol, Gemini 3.8 Flash, Grok 4.7, Composer 2.5.
  2. Plus an empty configuration (no extra index).
  3. Plus HypoPG greedy: the five and eight indexes with the largest summed optimizer-cost gain. That is a baseline, not the ground truth.
  4. build_configs.py drops unknown columns, tables under 1000 rows, indexes that already exist, and duplicates. Result: 33 configurations, 194 indexes, in results/configs_sf1.json.

4. How one configuration is timed

One configuration at a time, so they do not share indexes. Statistics are analyzed once per database and then frozen. Autovacuum is off. Each result row stores a statistics fingerprint.

CreateCREATE INDEX for every index in the set. Sum of those wall times is the build time.
→
Warm-upRun each query once and throw the time away.
→
TimeIf warm-up ≤ 2 s, two timed runs; else one. Report the median. Cap 20 s, counted as 20 s.
→
DropDROP INDEX, then the next configuration.
ScoreA(C) = Σq=1..99 median_time(q, C)     (primary)
ScoreB(C) = build_time(C) + ScoreA(C)     (secondary) Lower is better. A query that errors or hits the cap is recorded as 20 s. The same rule is used on D and on D'.

5. How a sample is built

TPC-DS is a snowflake: fact tables join to dimensions on foreign keys. If you sample two tables independently, the join is about p² of the original, often empty. That is why there is more than one sampler. After loading, primary keys are applied and VACUUM (ANALYZE) is run once.

Notation: table T has nT rows. Target rate p = pct / 100 (here 0.05). Seed s = 42. Fact tables are store/catalog/web sales and returns, plus inventory. Everything else is a dimension.

SQL:Trek sizing (used by Bernoulli and page)

kT = min( max(p · nT, 20 000), 1 000 000 · (p / 0.05), nT )
rT = kT / nT Floor 20 000 rows, cap 1 million at 5% (scaled with p). Tiny dimension tables are kept in full because rT hits 1.

B0. Bernoulli, independent per table

Each row of each table is kept independently. In PostgreSQL this is TABLESAMPLE BERNOULLI (100 r_T) REPEATABLE (s).

For row x in T:   P(x ∈ D') = rT
E[ |T'| ] = rT nT
For an FK join T ⋈ U on key k, if both are sampled:   E[ |T' ⋈ U'| ] ≈ rT rU |T ⋈ U| That product is the TPC-DS trap. At p = 0.05 the join is about 0.25% of the original if both sides shrink.

B1. Page sampling

Same target size rT, but whole pages are kept or dropped. TABLESAMPLE SYSTEM. Cheaper to build. Biased if values cluster on disk (TPC-DS loaded by COPY is ordered by date).

For page π of T:   P(π ∈ D') = rT
Rows in a kept page are all kept. Rows in a dropped page are all gone. Not IID. Adjacent keys are correlated. Fine as a cheap baseline; not a model of a uniform row sample.

C2. Universe on the item key

A hash of the item key decides membership, the same hash in every fact table. Dimension tables are copied in full. Per-item join fan-out is preserved. The set of items shrinks.

Keep buckets B = round(100 p) out of 10 000.
Keep fact row x iff   (hashs(item_sk(x)) mod 10 000) < B
Keep every dimension row. If two facts join on item_sk, a pair survives iff the item is in the kept universe. Expected fraction of such pairs is about p, not p². A query that filters on date still sees a full date_dim and a thinned fact.

C1. Foreign-key closure

Sample the three sales facts independently at rate p. Keep a returns row if its matching sale was kept. Keep inventory rows for sampled items, then Bernoulli-thin inventory at rate p. Dimensions in full.

Sales S:   P(row ∈ D') = p   (Bernoulli)
Returns R of sale s:   keep iff s ∈ S'
Inventory I: keep with probability p, among rows whose item appears in S'
Dimensions: copy in full This is a join synopsis on the sale → return edge. Sales of different channels are still independent of each other.

C3. Stratified on sold date

On each sales table, partition by sold-date key. Keep at least 5 rows per date, then keep further rows with probability p. Other facts use the Bernoulli sizing rule. Dimensions in full.

For sales table S, stratum d = sold_date_sk:
keep row x if rank_d(x) ≤ 5   or   Ux < p   (U uniform on [0,1]) Stops a rare date from vanishing. Not the full STRAT optimiser (Chaudhuri, Das, Narasayya 2007), which picks strata to minimise workload error. This is date-stratified sampling with a floor.

C4. Statistics transplant (not a different set of rows)

Keep the sample's rows. Overwrite pg_statistic and pg_class.reltuples / relpages with the full database's values. The planner is told the table is large. The index built on the sample is still small. Do not ANALYZE afterwards.

data(D') unchanged,   stats(D') ← stats(D) SQL:Trek listed this as future work ("virtual statistics"). The question is whether a wrong ranking was caused by the rows or by ANALYZE on the sample. Index statistics are not copied.

Not built

C5 workload-aware / predicate-witness sampling (keep rows the queries actually touch). That is still in the proposal and in the taxonomy. It was not implemented.

6. How the two rankings are compared

Let xC be ScoreA(C) on the full database and yC the same score on D'. There are n = 33 configurations.

Kendall tau-b: over pairs {C, C'}, count concordant vs discordant orderings of (x, y), with ties handled.
τ ∈ [-1, 1]. Interval: 1000 bootstrap resamples of the 33 configurations, 2.5 and 97.5 percentiles.

Top-1:   argmin_C yC  =?  argmin_C xC
Regret:   xpick / min_C xC   (1.0 is perfect)
Top-3: is argmin x among the three smallest y?
Cost reduction:   Σ_C (build + workload)_D  /  Σ_C (build + workload)D' The "including sample build" column adds the time in results/samples.jsonl to the denominator.
